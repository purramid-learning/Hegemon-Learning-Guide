Section 1

Problem Statement

A generic Socratic tutor responds to a wrong answer by asking a question. The question is drawn from a general repertoire — "What do you think the first step is?", "Can you walk me through your reasoning?", "What does that number tell you?" — and is selected without reference to why this particular student produced this particular answer. The system knows the answer is wrong. It does not know what is wrong.

This is not diagnosis. It is a conversational posture that resembles diagnosis. The distinction matters because the two failure modes it papers over are not equivalent, and they do not respond to the same intervention.

What generic Socratic bots do

The common implementation compares the student's response to a stored correct answer, branches on a boolean, and — on the false branch — passes the item text and the student's response to a language model with an instruction of the form "do not give the answer; ask a leading question." The model, having no representation of the student's error beyond the raw string, produces a question whose relevance is a matter of chance. Where the model does infer something about the error, the inference is unconstrained, unlogged, and unavailable to the rest of the system: it exists only inside a generation that is immediately discarded.

The result is a tutor that is reliably polite, reliably question-shaped, and unreliably useful. Two students who plot (−3, 2) at (2, −3) and at (3, 2) receive interchangeable prompts, though the first swapped the coordinates and the second mishandled a negative. Neither error is addressed. Both students are asked to try again in a friendlier voice.

Why that is insufficient

  • Scaffolding without a target is arbitrary. A rung is only a rung if it sits between where the student is and where the item requires them to be. Without locating the student, the system cannot place the rung; it can only place a rung.
  • The error signal is discarded. Because classification happens implicitly inside a generation, nothing downstream can act on it — not the item sequencer, not the teacher report, not the next turn of the same conversation.
  • Behavior is non-reproducible. Identical student input can yield materially different tutoring across runs. A pedagogical system whose diagnosis is a sampling artifact cannot be audited, regression-tested, or defended to a district.
  • Student work is sent to a third party. Handing raw student responses to a model API to be implicitly classified moves student data off local infrastructure for a task that, at this scope, does not require it.

What misconception-targeted scaffolding does differently

Hegemon separates classification from generation and assigns them to different layers with different implementation technologies.

Classification is performed first, deterministically, in client-side JavaScript, by comparing the target coordinate to the plotted coordinate against an ordered set of diagnostic rules. Each rule corresponds to a named, documented misconception. The layer emits a short code — MC-01, MC-06, MC-08 — or null when no rule matches.

Generation is performed second, by a language model that receives the code and the student's conversation history but is never asked to determine what went wrong. Its task is bounded: given that the error is axis transposition, produce the next single Socratic rung that surfaces the ordered-pair convention without stating the answer.

The consequence. The student who swapped coordinates is asked which of the two numbers tells them how far to move across. The student who mishandled a negative is asked what the minus sign does to the direction of travel. These are different interventions because the diagnoses are different, and the diagnoses are different because something in the system actually performed one.

Section 2

System Architecture Overview

The system is a static front end, a deterministic client-side diagnostic layer, a server-side proxy, and a language model API. There is no student data repository, no user accounts, and no persistent record of student work beyond the browser session.

Two student-facing surfaces feed the pipeline. The lesson page carries instructional content interleaved with invisible hg-marker elements (Section 3); as the student scrolls, a reader module records which markers have been passed and persists that record to sessionStorage. The practice grid presents a target coordinate and accepts a click-to-plot response.

When the student plots a point, the plotted coordinate and the target coordinate are passed to the detection module, which returns a misconception code or null. Misconception correction is gated behind an incorrect-response counter — it opens on the second wrong answer in an item group, not the first — so a student who self-corrects is not interrupted. Comprehension support has two ungated entry routes of its own (Section 6).

On activation, the code, the marker context package, and the conversation history are posted to a Firebase Cloud Function. That function validates the payload shape, checks the request origin against an allow-list, enforces a per-IP rate limit through a Firestore transaction, assembles the system prompt from the invariant rule block and a runtime session-context block, and calls the Claude API using a key held in Cloud Functions secret configuration. The key is never present in client code. On return, the function parses the generation: it extracts bracketed control tokens, strips them from the learner-visible text, and returns the cleaned rung together with structured flags the client uses to drive interface behavior.

The student answers, the answer is appended to the conversation history, and the cycle repeats until the item resolves, the student dismisses the guide, or the scaffold stalls and escalates to a human teacher. The misconception code is set once, at conversation start, and carried unchanged through the conversation; subsequent turns do not re-classify.

Deployment

  • Front end — static HTML, CSS, and vanilla JavaScript in UMD modules. No build step, no framework, no bundler. Served from GitHub Pages.
  • Proxy — Firebase Cloud Functions (2nd generation), Node.js, us-central1. Rate limit: 20 requests per IP per hour, enforced in a Firestore transaction so the count is consistent across function instances.
  • Model — Anthropic Claude, invoked through the official SDK with a bounded max_tokens so a single response cannot exceed one scaffolding turn.
  • Tests — dependency-free Node harnesses over the pure modules; the detection layer is fully testable without a browser, a network, or a model.

Section 3

The Marker System

I designed the marker system to answer a question that a tutoring bot cannot ask a fourth grader and expect a usable answer: what part of this are you stuck on? Students who are confused are, by construction, poorly positioned to name the source of their confusion. Asking them to self-report produces either silence or a restatement of the item text.

The marker system moves that burden off the student and onto the instructional content. Concepts are annotated at authoring time with invisible semantic metadata embedded directly in the lesson HTML. At bot activation, the system reads which annotations the student has actually passed and uses them to scope the diagnostic context.

Marker element structure

A marker is an empty <span> carrying the class hg-marker, three data attributes, and aria-hidden. It is styled display:none, so it never renders, never occupies layout, and is never announced by a screen reader. It is placed adjacent to the visible element that teaches its concept.

Marker anatomy

<span class="hg-marker"

data-prereqs Comma-separated list of topic identifiers this concept depends on. May be empty. Directed edges in the concept graph. Enables prerequisite routing (CG-04): when a student's stated confusion does not resolve, the system walks upstream rather than re-explaining the same node.
data-likely-misconceptions Comma-separated MC codes this concept is known to produce when imperfectly held. Authoring-time prior. Narrows the plausible error space before any student response exists, and lets the system flag concepts a student skipped past.

The full lesson carries seventeen markers spanning number-line through zero-coordinate. Together their data-prereqs edges form the lesson's concept graph, authored inline with the content it describes rather than maintained as a separate model that can drift out of sync with the page.

How the reader works

The reader module (marker-reader.js) exposes two public operations: track(), called once on the lesson page, and read(), called at bot activation on either page.

Anchoring

Because a marker is display:none, it has no geometry and cannot itself be tested against the viewport. Each marker is therefore anchored to its nearest visible sibling — the paragraph or figure it sits beside — falling back to its containing section. Scroll position is measured against the anchor.

Seen tracking

A marker is recorded as encountered once its anchor's top edge has risen above a configurable fraction of viewport height (default 1.0 — the anchor has appeared from the bottom edge). Tracking is monotonic: scrolling back up never un-sees a marker. Scroll and resize handlers are passive and coalesced into a single requestAnimationFrame sweep.

Persistence

Encountered markers are written to sessionStorage under a versioned key. This is what allows the bot to open on the practice grid — a page containing no markers at all — and still know what the student read. On the lesson page, read() merges live scroll state with the persisted snapshot; on the practice grid, it falls back to the snapshot alone. Storage failures are caught and degrade to an empty set rather than throwing.

Activation focus

When the student launches the bot by tapping a bolded term rather than by plotting a wrong point, read({ focus }) resolves that term to a topic and surfaces it as ctx.focus. Focus also sets the encountered cutoff — tapping a term implies having reached it — so the context reflects the student's position in the lesson even if scroll tracking was incomplete. Resolution prefers an authoring-time data-focus-topic attribute and falls back to a display-string lookup table.

Context package

The output is a plain object: the ordered list of encountered marker records, the distinct topicsSeen, the sorted union of their likely misconception codes, the prereqEdges adjacency list, the focus record if any, a provenance field (live, persisted, focus, or empty), and a capture timestamp. This object is what crosses the network boundary. It contains topic identifiers and misconception codes. It contains no student text, no answers, and no identifiers.

Boundary. The reader supplies context and nothing else. It performs no detection, no scoring, and no model call. Its pure helpers — list splitting, marker parsing, context building — are DOM-free and unit-tested in a dependency-free Node harness; only the scroll and persistence glue touches the browser.

Why this beats the alternatives

  • Versus open-ended self-report. "What are you confused about?" asks the student to perform the metacognitive act they are failing at. The marker system infers scope from behavior the student is already producing — reading — instead of requesting a diagnosis from the person being diagnosed.
  • Versus page scanning. Extracting concepts by scraping rendered text and inferring structure is lossy, brittle under layout change, and produces no prerequisite relationships. Markers carry the author's intent explicitly: this paragraph teaches this concept, which depends on these, and tends to produce these errors. That is knowledge the page text does not contain and cannot be reliably recovered from it.
  • Versus a separate concept-model file. A graph maintained apart from the content drifts as soon as the content is edited. Co-locating the annotation with the paragraph it describes makes divergence visible in the same diff.
  • Versus sending page content to the model. Shipping lesson text to an API for the model to interpret is slower, costlier, non-deterministic, and unnecessary — the relevant structure was known at authoring time and compresses to a handful of identifiers.

Section 4

Misconception Taxonomy

The taxonomy is scoped to Lesson 1 — Finding Points on the Coordinate Plane: four quadrants, integer coordinates, grid extent −5..5. Notation: target is the point the task asked for, plotted is where the student clicked, and named quadrant is the Roman numeral the student assigns (MC-04 only).

Two code families exist. MC (Misconception) codes describe assessment errors — a wrong plot or a wrong quadrant name — and are inferred by the detector. CG (Comprehension Gap) codes describe self-identified confusion about instructional content and carry no diagnostic rule, because the student points at the concept directly. Both operate under the same behavioral contract (Section 6). Each code below records the misconception, its diagnostic rule, and the scaffolding goal — what the Socratic prompt should help the student discover, never what it should tell them.

MC-03Steps 4–5 — start at the origin, count the spaces

MC-06Step 5 — distance vs. direction with negatives
MC-07Step 5 — a 0 coordinate sits on an axis

Misconception

Goal

MC-02Sign / Directionality Error
Misconception
Student travels the right distance but the wrong direction on one or both axes — e.g., right instead of left for a negative x.
Diagnostic

MC-03Origin / Offset Error

Student starts counting at 1 instead of 0, or counts gridlines instead of the spaces between them, producing a consistent off-by-one shift.
Diagnostic
Signs correct on both axes, and plotted − target is a constant nonzero offset (commonly ±1) on one or both axes. Most reliable across several plotted points.
Goal
Surface where counting begins — the origin is 0, not 1 — and that each step counts a space between gridlines.

MC-04 — Quadrant Numbering Errors

Naming a quadrant is a separate skill from plotting a point: it asks the student to apply the I–IV numbering scheme to a location. Whether any point was plotted correctly is irrelevant. The input is a named quadrant for a location whose corner is already known from the signs of its coordinates — not a plotted coordinate.

The correct scheme starts at the top-right corner (+x, +y = Quadrant I) and counts counterclockwise. Two independent things can go wrong — the starting corner and the direction — producing MC-04a through MC-04c. MC-04d is a distinct schema mismatch that the two-knob model cannot generate.

Corner (signs)CorrectMC-04aMC-04bMC-04cMC-04d

top-left (−, +)IIIIVII
bottom-left (−, −)IIIIIIIIIVIII

MC-04aIncorrect Starting Point
Misconception
Student counts counterclockwise (correct direction) but begins in the wrong corner — numbering the top-left as Quadrant I, the way an English reader starts at the top-left of a page. Every quadrant's number shifts one position around the plane.
Diagnostic
Named quadrants match the MC-04a column — e.g., a top-right location named IV, or a bottom-left location named II. Independent of whether the point itself was plotted correctly.
Goal
Surface where the numbering begins — Quadrant I is the top-right corner, where both coordinates are positive, not the top-left.
MC-04bClockwise Numbering
Misconception
Student begins in the correct corner (top-right) but counts clockwise. Quadrants I and III — the start and its diagonal opposite — keep their correct numbers; II and IV swap.
Diagnostic
Named quadrants match the MC-04b column. Tell-tale single responses: a top-left location named IV, or a bottom-right location named II.
Goal
Surface the direction of the count — quadrants are numbered counterclockwise, not clockwise.
MC-04cIncorrect Start and Clockwise
Misconception
Both errors at once — student begins at the top-left and counts clockwise. Relative to the correct scheme, the top corners swap numbers (I↔II) and the bottom corners swap (III↔IV).
Diagnostic
Named quadrants match the MC-04c column. Tell-tale single responses: a top-right location named II, or a bottom-left location named IV.
Goal
A compound error — scaffold one knob at a time, never both in one prompt. First surface the starting corner (Quadrant I is the all-positive corner); confirm; then surface the direction (the next number sits where x flips sign but y holds).
MC-04dRow-by-Row (Raster) Numbering
Misconception
Student numbers quadrants in reading order — top-left, top-right, then bottom-left, bottom-right — rather than starting at the all-positive corner and counting counterclockwise. This is a schema mismatch, not a rotation error: the two-knob model that produces MC-04a/b/c cannot generate the raster pattern, so it sits outside that family.
Diagnostic
Named quadrants match the MC-04d column. A top-right location named II is shared with MC-04c; a bottom-corner response is needed to separate them, since MC-04c assigns BL=IV/BR=III while MC-04d assigns BL=III/BR=IV. MC-04d matches the correct scheme on both bottom corners, so this student looks correct on any bottom-corner or axis probe and can only be identified from a top-corner response.
Goal
Scaffold start corner and direction one at a time, as for MC-04c. First surface where Quadrant I is; confirm; then surface the direction of counting.
MC-05Reflection Axis Confusion — reserved
Status
Out of scope for this lesson. The lesson introduces signs and quadrants but never asks students to reflect a point, so there is no task for this code to fire on. The number is reserved, not reused, so codes stay aligned with the master template; the full entry is restored when a reflection activity enters scope.
MC-06Magnitude / Sign Conflation
Misconception
Student gets both distances from the origin right but mirrors the point — right place, wrong direction.
Diagnostic
abs(plotted_x) == abs(target_x) and abs(plotted_y) == abs(target_y), but one or both signs are wrong. Checked before MC-02.
Goal
Affirm that both distances from the origin are correct, then surface which direction each sign points — this is what distinguishes it from an MC-02 case where a distance may also be wrong.
MC-07Axis-as-Boundary
Misconception
Student pushes a point with a 0 coordinate off the axis into a neighboring quadrant, instead of placing it on the axis.
Diagnostic
target_x == 0 or target_y == 0, and the plotted point does not lie on that same axis.
Goal
Surface that a coordinate of 0 means no movement along that axis, so the point sits on the axis, not inside any quadrant.
MC-08Incomplete Plot / Axis Collapse
Misconception
Student makes only one of the two moves — travels across but not up, or up but not across — and stops on an axis. Maps directly to the lesson's "across, then up" two-step.
Diagnostic
target_x != 0 and target_y != 0 (target is inside a quadrant), but plotted_x == 0 or plotted_y == 0.
Goal
Surface that a point inside a quadrant needs both an across move and an up/down move from the origin — did they make both?

Detection order

The plotting codes are evaluated in a fixed sequence, first match wins. Order encodes precedence between overlapping signatures: more specific rules run before looser rules that would otherwise claim their cases.

#CodeRationale for this position
1MC-01Runs first so a swapped pair is not misread as a direction error. A transposition frequently satisfies a sign rule incidentally; checking it first preserves the correct diagnosis.
2MC-07Zero-coordinate targets are a distinct structural case. Handled before the general sign and offset rules, which are not meaningful when the target lies on an axis.
3MC-08The mirror case: target inside a quadrant, plot on an axis. A collapsed plot would otherwise be absorbed by the offset rule when the collapse happens to be one unit.
4MC-06Both magnitudes exact, at least one sign wrong. Checked before MC-02 so the scaffolding can affirm the correct distance first — pedagogically distinct from the looser sign error, and the only place that affirmation is warranted.
5MC-02The looser sign error: a clean sign flip on at least one axis, with the other axis possibly wrong in magnitude too. Reached only after the exact-mirror case is gone.
6MC-03Last of the chain. The off-by-one signature is the weakest and would otherwise capture near-miss plots that belong to a more specific code.

MC-04 dependency

MC-04a–d cannot fire from plotted coordinates alone. A click-to-plot grid yields only a coordinate; quadrant numbering errors are only observable when the activity asks the student to name a quadrant. MC-04 is therefore implemented as a separate detector, keyed to a named quadrant and the corner the location occupies, and is not part of the coordinate evaluation chain.

A single naming response is often ambiguous — a top-right location named "I" fits both the correct scheme and MC-04b. With five candidate schemes, probe choice determines identifiability:

  • Left or right column (TL+BL, or TR+BR) — either pair uniquely identifies all five schemes. These are the recommended probes.
  • Top row (TR+TL) — cannot separate MC-04c from MC-04d; both assign TL=I, TR=II.
  • Bottom row (BL+BR) — cannot separate the correct scheme from MC-04d; both assign BL=III, BR=IV.
  • Diagonal pairs (TR+BL, TL+BR) — insufficient; TR+BL cannot separate the correct scheme from MC-04b.
  • Three or more distinct-quadrant probes always resolve the scheme, since the fourth corner is then forced.

MC-05 omission

MC-05 (Reflection Axis Confusion) is present in the master taxonomy template but omitted from the live set for this lesson, because the lesson contains no reflection task and the code therefore has nothing to fire on. The number is held rather than recycled. Renumbering would silently invalidate every marker attribute, test fixture, prompt, and stored code that references the existing set; the cost of an unused integer is lower than the cost of an ambiguous one. The same rule governs extension: a family is extended by sub-lettering (MC-04d, CG-01a), never by renumbering.

Fallback handler

Deterministic detection does not cover every stray plot, and it is not intended to. When no rule matches, the detector returns null and the conversation is routed to an unclassified handler: the model is told explicitly that no misconception was identified and is instructed to probe generically — "walk me through how you placed that point" — rather than asserting a diagnosis it cannot substantiate.

This is a deliberate design commitment. A system that always produces a label is a system that produces wrong labels, and a confidently wrong diagnosis is worse for a student than an honest question. The null return is a first-class outcome, not an error path.

Comprehension gaps — the CG family

The MC family covers errors the student has already made. The CG family covers confusion the student reports before or independent of any assessment — a student who has bounced off the material and has no wrong answer to diagnose. There is no detector and no evaluation order here: a comprehension gap is self-identified, the student points at a concept (a tapped term, an "I don't get this"), and the marker reader supplies it as ctx.focus. The five codes are a routing aid for which rephrase move fits, not a classifier.

CodeGapMove
CG-01Definitional — "what is this?"Rephrase the lesson's framing in concrete words anchored to a worked instance, then end on a check the student answers.
CG-02Procedural — "how do I do this?"A request about the method gets a conceptual rephrase; a request to do this specific item is the assessment question asked in advance, and is handed to decomposition instead.
CG-03Rationale — "why is it like this?"Connect the rule to what the student already knows, then ask them to predict a consequence. The prediction is the rung — do not lecture the reason.
CG-04Prerequisite — the gap is upstreamRoute up the concept graph using the marker prereqEdges: probe the prerequisite, rephrase it if shaky, confirm, then return to the named concept. One level at a time.
CG-05Discrimination — two terms conflatedDo not state the distinction. Give a concrete case and ask the student to sort it; the contrast is drawn by their answer.

Section 5

Deterministic Detection Layer

The detection module is pure: no DOM, no network, no Firebase, no model. It is a function from four integers to a string or null.

Signature

InputTypeMeaning
target_x, target_yintegerThe point the task asked for.
plotted_x, plotted_yintegerWhere the student clicked.

The function accepts either four positional integers or a single record object, normalizes the two forms, and throws a TypeError if any of the four values is not an integer. Non-integer input is a client wiring bug, not a student error, and is surfaced loudly rather than absorbed into a misconception code.

Output: a misconception code string ("MC-01", "MC-02", "MC-03", "MC-06", "MC-07", "MC-08") or null. null is returned in two distinct situations: the plot is correct, or no rule matched. Both mean "do not assert a misconception," and the caller distinguishes them by checking correctness separately.

Rules, in evaluation order

Each predicate is written to be true on its own signature in isolation. Precedence between overlapping signatures is handled entirely by order, never by conditions inside the predicates — which keeps each rule independently readable and independently testable.

Guard — evaluated before the chain

if (plotted_x === target_x && plotted_y === target_y) return null;   // correct plot

1 · MC-01 — Axis Transposition

target_x !== target_y
  && plotted_x === target_y
  && plotted_y === target_x

The target_x !== target_y guard excludes symmetric pairs such as (3, 3), where a swap is unobservable and any match would be spurious.

2 · MC-07 — Axis-as-Boundary

(target_x === 0 && plotted_x !== 0)
  || (target_y === 0 && plotted_y !== 0)

3 · MC-08 — Incomplete Plot / Axis Collapse

target_x !== 0 && target_y !== 0
  && (plotted_x === 0 || plotted_y === 0)

4 · MC-06 — Magnitude / Sign Conflation

abs(plotted_x) === abs(target_x)
  && abs(plotted_y) === abs(target_y)
  && !(plotted_x === target_x && plotted_y === target_y)

5 · MC-02 — Sign / Directionality Error

(target_x !== 0 && plotted_x === -target_x)
  || (target_y !== 0 && plotted_y === -target_y)

The target !== 0 guards prevent a negative-zero false positive. Because MC-06 has already run, the exact-mirror case is gone by this point; what reaches MC-02 is a sign flip on one axis with the other axis also wrong in magnitude.

6 · MC-03 — Origin / Offset Error

dx = plotted_x - target_x
dy = plotted_y - target_y
(dx !== 0 || dy !== 0) && abs(dx) <= 1 && abs(dy) <= 1

This is the single-point proxy for the taxonomy's "consistent off-by-one shift across several plots." A constant offset cannot be verified from one plot, so the implemented rule is deliberately conservative: only exact ±1 offsets qualify. Anything looser falls through to the fallback rather than being labeled on thin evidence. Widening this rule would trade a small gain in coverage for a large loss in precision, and precision is what makes the label worth acting on.

Separate detector · MC-04 — quadrant naming

detectQuadrantError(corner, named)
  corner ∈ { "TR", "TL", "BL", "BR" }     // derived from the signs of the coordinates
  named  ∈ { "I", "II", "III", "IV" }     // the Roman numeral the student assigned

  if named matches the correct scheme for corner  → null
  else return the first scheme in [MC-04a, MC-04b, MC-04c, MC-04d]
       whose mapping for corner equals named
  if no scheme matches                            → null   (unclassified)

This detector is a table lookup against the five candidate schemes. A single response identifies a best guess; disambiguating between schemes that agree on the probed corner requires a second probe from the appropriate column (Section 4).

Why deterministic rather than learned

At this scope a classifier would be strictly worse, and not marginally so.

  • The error space is small, closed, and known. Coordinate plotting on a −5..5 integer grid admits a bounded set of procedural failures, each with an exact algebraic signature. There is nothing here for a model to discover that a curriculum specialist has not already named.
  • Rules are exhaustively verifiable. Every target–plot pair on the grid can be enumerated and the detector's output checked against the taxonomy. No classifier offers that guarantee.
  • Behavior is reproducible. The same input yields the same code on every run, on every machine, forever. Tutoring behavior can be regression-tested; a change in scaffolding is traceable to a change in a rule.
  • No training data is required — therefore no collection of student work, no labeling pipeline, no cold-start problem, and no drift.
  • The rules are legible to educators. A teacher can read "the student plotted the mirror of the target with both distances correct" and either agree or object. The rule is the explanation; there is no post-hoc interpretability layer, because there is nothing opaque to interpret.
  • It runs client-side in microseconds with no inference cost and no network round trip, which is why classification can complete before any data leaves the browser.

Boundary condition — free text

Deterministic detection ends where structured input ends. The rules above operate on a plotted coordinate — a constrained response with an exact algebraic relationship to the target. A student who instead types "I went up 3 and then over 2 but the minus confused me" has produced a response with no such relationship. There is no rule to write.

This is a real limit of the approach, not a temporary implementation gap. Classifying free-text mathematical reasoning into a misconception taxonomy is a natural-language classification problem, and it is the boundary at which a trained classifier becomes the right tool rather than a redundant one. The architecture anticipates that boundary: because classification is an isolated layer with a fixed contract — response in, code out — a text classifier can be added as a sibling detector, emitting codes into the same taxonomy and the same generation pipeline, without altering the generation layer at all. In this demo, free-text input is routed to the unclassified handler.

Section 6

Scaffolding Generation Rules

The model's role is bounded by contract. It receives a misconception code and marker context; it does not determine what the student got wrong, and it is not asked to. Its task is to produce the next single rung of a scaffold aimed at an already-identified target.

The system prompt is assembled server-side from the behavioral contract plus a session context block carrying the code, the task type, and the marker context. The rules below are the contract. They are not stylistic preferences; they are the conditions under which the output is pedagogically valid, and relaxing any of them changes what the system is.

Two modes

Hegemon is a scaffolding guide, not an answer key. It operates in two modes, which are one continuous guide rather than two bots — a student can hit comprehension support while reading, then misconception correction after plotting wrong.

  • Comprehension support — the student signals confusion about something they are reading, before or independent of any assessment. Technique: rephrase. Re-present the instructional content in more digestible form, toward a question. The terminal question is a check: the student applies the just-rephrased idea to confirm it landed.
  • Misconception correction — the student's response reveals a procedural error. Technique: decompose. Break the question into smaller sub-questions. The terminal question elicits the withheld answer: the rungs lead up to the assessed result and the student supplies the last step.

The rules

  1. Never state the assessed item. The bar is on the specific result the task checks — which quadrant, which coordinate, which point. Definitions and conventions are not the assessed item; they are the rungs that lead to it, and the system surfaces them freely. The word "axes," the I–IV numbering scheme, and "across-then-up" order are conventions — re-surfacing them is rephrasing, not answering.
  2. Every rung ends in a question the student answers.
  3. One rung per turn. The student responds before the next rung appears. No front-loading of multiple hints.
  4. Stop early. The moment the student can carry it, hand off — the minimum rungs, never a full walk-through. The failure mode to avoid is ten minutes of step-by-step that a student extracts instead of two minutes spent thinking.
  5. One component at a time. Compound errors are addressed in sequence — surface one, resolve it, confirm, then move to the next. MC-04c is two errors at once (wrong start corner and wrong direction); the system scaffolds the start corner to resolution before mentioning direction. Never stack two corrections in one prompt.
  6. Acknowledge before redirecting. Never a cold "try again." What the student did is acknowledged before the redirect. For MC-06 specifically, both distances from the origin are correct and the acknowledgment says so — that is the whole pedagogical difference between MC-06 and MC-02.
  7. Confirm the student's selection before continuing.
  8. Charitable interpretation. Ambiguous input produces 3–4 plausible numbered interpretations, always ending with an open "in your own words" option; the system confirms the pick before proceeding. The student is never told they were unclear.
  9. Zero-coordinate responses are always correct on direction. When a coordinate value is 0, any directional qualifier is vacuously true — "0 up" and "0 down" are equally correct for y = 0. Do not redirect. This applies especially when the system itself introduced the directional language; the student is answering in the terms the question provided.
  10. Coordinate value as positional answer. When a student answers a question about which coordinate by giving a coordinate value, identify which position that value occupies in the ordered pair and treat the answer as a positional claim, then evaluate that claim. If the target is (−3, 2) and the question is which coordinate moves left or right, the answer "−3" identifies the first coordinate — which is correct.
  11. Plain vocabulary. Language a ten-year-old would use naturally. "Relative" is banned: "above or below the x-axis," not "relative to the x-axis." Never join two questions with "and," "but," or "so" — if a draft contains "and" connecting two things the student must answer, everything after "and" is deleted and saved for the next turn.

Worked example — assessment mode, MC-04

The student was asked to label the quadrants and is stuck. Rungs are delivered one per turn; the student answers each before the next appears. Start and direction are addressed separately (rule 5), and the system hands off the moment the pattern is established (rule 4). Direction is framed through sign changes, not "counterclockwise" — the assessment measures the sign-to-quadrant link, so the feedback uses the same concept.

Rung 1 · Hegemon

The axes split the grid into four numbered quadrants. The numbering has two parts — where it starts, and which way it goes. Start with where it starts.

student responds

Rung 2 · Hegemon

Quadrant I is the corner where both coordinates are positive. Which corner is that?

student responds · system confirms the answer before continuing

Rung 3 · Hegemon

From Quadrant I, the next number sits where x flips negative but y stays positive. Which corner gets II?

student responds · system confirms the answer before continuing

Rung 4 · Hegemon

You've got the rule now — where do III and IV land?

Every rung states a convention and makes the student supply which corner is which. At no point is a quadrant assignment stated by the system.

Worked example — comprehension mode

Student · taps "axes"

I don't get "axes."

Hegemon

"Axes" is just the plural of "axis" — the lesson crossed two number lines to build the grid, and each of those lines is one axis. One runs side to side, the other up and down. Which one would you call the across line?

The label is re-surfaced (a convention, not an answer), the concept is rephrased concretely, and the turn ends on a check the student answers.

Two quadrant task formats

Quadrant tasks arrive in two shapes, distinguished by whether the payload carries a coordinate. The absence of a coordinate is the signal; the client omits it deliberately for that format.

  • Name recall (no coordinate) — the student was given a quadrant number and asked to click its location. The assessed item is where the quadrant sits. Scaffold via the numbering frame: anchor Quadrant I by the all-positive rule, then reason one sign change per transition. Never reference a coordinate — the student never saw one.
  • Coordinate identification (coordinate present) — the student was shown a point and asked which quadrant contains it. Scaffold from the coordinate's signs: x's sign gives left/right, y's sign gives up/down, one coordinate per turn.

Activation — three routes, one gated

The guide does not open on every wrong answer. Opening on the first error interrupts a student who was going to self-correct on the second attempt, which is the more valuable event. There are three entry conditions:

  • Term activation — the student taps a marked term in the lesson. Opens directly into comprehension support, with the tapped term resolved to a topic and supplied as ctx.focus.
  • Persistent help control — the student opens the guide unprompted. Opens into comprehension support; because no term was named, the student is offered a topic disambiguation list built from the markers they have passed.
  • Error threshold — gated by an incorrect-response counter. Misconception correction opens after two wrong answers within the same item group, not on the first. The counter resets on a correct answer.

Control tokens

The model's output carries a small closed vocabulary of bracketed control tokens. The proxy extracts them, strips them from the learner-visible text, and returns them as structured boolean fields alongside the response; the client reads those fields to drive interface behavior. The learner never sees a token.

TokenEffect
[CHOICES]Emitted with a numbered list of 3–4 interpretations; the client renders them as selectable buttons. This is the mechanical implementation of rule 8, and its use is restricted to charitable interpretation — numbered lists are not permitted anywhere else in the output.
[GRID_PROMPT]Requests that the student demonstrate a move by clicking the live assessment grid rather than describing it in words. Assessment mode only.
[QUADRANT_PROMPT]Requests a quadrant selection on the live grid. Assessment mode only.
[NEXT_QUESTION]Marks the scaffold resolved and surfaces the advance control.
[DISMISSED]Emitted when the student signals they are done ("I get it," "never mind"). Scaffolding stops immediately; no follow-up question is asked.

The grid tokens exist because of a constraint the contract imposes: the guide is forbidden from asking a student to point at, trace, circle, or otherwise physically interact with a grid, because the dialogue panel contains no grid to point at. All guidance must be expressible in words alone — except through these two tokens, which direct the student to the real assessment grid. This is possible because the panel is docked rather than modal: the assessment region stays live and interactive while the dialogue is open, so the student's click lands on the same grid they are being assessed on and re-enters the conversation as an input.

Escalation — the terminal path

Scaffolding can fail. When it does, the system's terminating move is to defer to a human, never to supply the answer:

  • Stall. If the student has been stuck on the same rung for two or more turns, the guide first tries a different angle — a more concrete example, a simpler sub-question — rather than repeating itself. If that also fails to produce progress, it escalates: "This might be a good time to ask your teacher for help."
  • Failed demonstration. If a grid or quadrant demonstration comes back wrong, the guide escalates on the very next turn rather than re-scaffolding with further questions. The single exception is MC-03, whose scaffold is a three-step sequence (origin, then x-axis, then the full point); there, a wrong step may be re-prompted once with the relevant definition supplied freely, and escalates if the same step fails again.

The escalation is detected server-side by pattern-matching the generated text and returned as a flag, which the client renders as a visually distinct turn. Rule 1 holds through the escalation: the terminal state of a failed scaffold is a referral to a teacher, not a disclosure of the assessed item. There is no state in this system that supplies the answer.

Server-side enforcement

The contract is enforced structurally as well as by prompt. The proxy validates that the misconception code matches the expected pattern, that the conversation history is a non-empty array ending in a user message, that every message carries a permitted role and non-empty string content, and that history length stays within a bounded window. Output length is capped so a single response cannot expand into a multi-rung walk-through, which is the most likely way rule 3 would fail in practice. Post-generation, the proxy strips control tokens and normalizes punctuation deterministically before the text reaches the learner.

Section 7

Two-Stage Pipeline Distinction

This section states explicitly what the Hegemon architecture is and is not, because the surface resemblance to two adjacent categories of system — predictive analytics platforms and LLM-classifier tutors — obscures differences that are architectural rather than incidental.

Classification of an observed action, not prediction of a future one

Hegemon classifies an action the student has already taken. The input is a plotted coordinate that exists; the output names the procedural error that produced it. The system makes no claim about what the student will do next, what grade they will earn, whether they are at risk, or how they compare to a cohort.

This is the load-bearing distinction from early-warning and predictive-intervention systems. Those systems model a student trajectory from accumulated history and output a forecast — a risk score, a completion probability, a recommended intervention tier. They require longitudinal data by construction; the forecast is a function of history. Hegemon's diagnosis is a function of exactly one response and the coordinate it was compared against. Nothing about the student's past is an input, because nothing about the student's past is relevant to the question "is this specific plot a transposition or a sign error?"

No historical data in the diagnostic path

The claim here is specific and should be read narrowly: the diagnostic path reads no stored record.

  • No training data. The detection rules were authored from the taxonomy. No student work was collected or labeled to produce them, and none is needed to maintain them.
  • No repository read. Detection's only inputs are the target coordinate and the plotted coordinate for the item in front of the student. It queries no database, consults no profile, and has no access to prior items. Marker state lives in browser sessionStorage and expires with the tab.
  • Stateless across sessions and items. The same plot yields the same code whether it is the student's first attempt or their fiftieth. No mastery estimate, learner profile, or trajectory is computed or stored.
  • No identity in the pipeline. The scaffolding endpoint receives no account, no login, and no identifier linking one response to another.

What the server does persist — stated in full

Accuracy on this point matters more than a stronger-sounding claim, so the server's writes are enumerated rather than characterized. The demonstration deployment persists three kinds of record, none of which is an input to detection or to scaffolding:

CollectionContentsPurpose
rate_limits A per-IP request counter and window start. No student work of any kind. Abuse control on the public demo endpoint.
demo_visitors Optional self-supplied name, organization, and email from the landing page, plus a transcript opt-in flag. Demonstration lead capture. Supplied by the adult evaluating the demo, not by a student, and optional in full.
transcripts The tutoring conversation, written only when the session carries an affirmative opt-in. The opt-in flag is re-verified server-side against the visitor record before any write; a client cannot forge it, and non-opted-in sessions are discarded silently. Reviewing scaffolding quality during the demonstration. Not read back by any part of the running system.

These are properties of a public demonstration deployment — lead capture and opt-in quality review — not of the tutoring architecture. Removing all three would leave detection and scaffolding functionally unchanged, which is the test that distinguishes an architectural data requirement from a deployment convenience. A predictive system cannot pass that test: remove its learner record and the prediction cannot be computed at all.

The deterministic layer is not a model

The detection layer is roughly a hundred lines of ordinary JavaScript: comparisons, absolute values, and a fixed-order loop. It is not a transformer, not a neural network, not a statistical classifier of any kind. It has no parameters, no weights, no training procedure, and no inference step. Its behavior is fully specified by the rules in Section 5 and is exhaustively enumerable over the finite grid.

Two stages, two technologies, one direction of flow. Stage one — deterministic rules — decides what is wrong. Stage two — a language model — decides how to ask about it. The output of stage one is an input to stage two. Nothing flows the other way. The model's generation never becomes a diagnosis, is never stored as one, and cannot influence the code that produced it.

Generation only — an architectural constraint

That the model does not classify is a property of the system's construction, not a limitation of the model. Claude is fully capable of attempting a diagnosis; the architecture declines to ask it for one, and the contract gives it nowhere to put one. The system prompt supplies a code that has already been determined. The conversation carries no request to identify an error type.

The response contract does carry structure — the control tokens described in Section 6 — so the claim must be stated precisely rather than as "text only." Every token is an interaction-control signal; none is a classification. They request a grid demonstration, offer an interpretation list, mark the item resolved, or mark the session dismissed. There is no token by which the model could assert a misconception, and the code field in the response payload is the client's own code echoed back for correlation — it is copied from the request, never read from the generation. A model response that contradicted the detected code would change no code, be stored as no diagnosis, and be read by no consumer.

The constraint is what buys the properties the system depends on: reproducible diagnosis, auditable rules, regression-testable tutoring behavior, and a classification step that can be verified without invoking a model at all. A system in which the model classifies has none of these, regardless of how well the model classifies.

FERPA implication

Because classification completes in the browser before any network call, the data crossing the boundary to the model API is: a misconception code from a fixed vocabulary, a list of lesson topic identifiers, a prerequisite adjacency list, and the tutoring conversation itself. The student's plotted coordinate, the target coordinate, their score, their history, and their identity are not transmitted.

The architectural point is stronger than the current implementation. Because the diagnostic step is separable and requires no model, the whole classification stage can run on local or district-controlled infrastructure, with only an anonymized code reaching a third-party API — or, with a locally hosted model, nothing leaving at all. A system in which the model performs classification cannot make this separation, because the raw student response must reach the model for classification to occur. The separation is available here precisely because the two stages were built as two stages.

Scope note. This describes the architecture's properties, not a compliance certification. Deployment in a school setting requires its own review; the point here is that the architecture does not foreclose that review by construction.

Prior Art Search Notes

The publication below is the nearest art identified to date. The distinguishing factors are stated with respect to the architecture disclosed above — principally the separation of deterministic classification from generative scaffolding, the authoring-time marker graph, and the absence of any historical student data requirement in the diagnostic path.

Publication no.TitleDistinguishing factors
US 2025/0348966 A1 System and Method for Transformer-based Student Performance Prediction and Reasoning-Enhanced Intervention Planning for Objective Assessment of Learning Outcomes

Object of the inference. The reference infers a predicted future performance outcome. Hegemon infers the procedural error present in a response the student has already submitted. These are different inferential targets, not different accuracies at the same target: a Hegemon diagnosis makes no claim about what the student will do next, and a performance prediction identifies no specific error to scaffold against.

Classification technology. The reference classifies with a transformer. Hegemon's classification stage has no model, no parameters, no weights, and no training procedure — it is an ordered set of algebraic comparisons on four integers (Section 5), exhaustively enumerable over the finite grid.

Data requirement. Transformer-based performance prediction is a function of accumulated learner history; the forecast is definitionally a function of the record. Hegemon's diagnostic path reads no stored record of any kind — its inputs are the target coordinate and the plotted coordinate for the single item in front of the student (Section 7).

Basis of the intervention. The reference plans an intervention from a predicted outcome. Hegemon selects scaffolding from a named misconception code drawn from a closed, published taxonomy (Section 4), so the intervention is traceable to an identified error rather than to a risk estimate.

Role of the generative model. Hegemon's language model is architecturally barred from classifying: it receives an already-determined code and returns a single scaffolding turn, and no field in the response contract carries a diagnosis (Section 7).

Instructional-content instrumentation. No counterpart to the authoring-time marker graph — non-rendering topic, prerequisite, and likely-misconception metadata embedded in the lesson and read from scroll position at activation (Section 3).

On the axis of distinction. "Predictive versus deterministic" conflates two independent separations, and stating them separately is stronger than stating either alone. Predictive contrasts with retrospective — whether the system infers a future outcome or classifies an action already taken. Learned contrasts with rule-based — whether the inference comes from trained parameters or from fixed logic. The reference is predictive and learned; Hegemon is retrospective and rule-based. Each separation stands on its own: a rule-based predictor and a learned retrospective classifier would both be distinct from Hegemon, and for different reasons.

Framework for assessing further references

Three separations recur as points of distinction and are recorded here as the framework against which additional references should be assessed:

  1. Object of the inference. Systems whose output is a forecast, risk score, mastery estimate, or completion probability differ from a system whose output names the specific procedural error in one observed response.
  2. Classification technology and data requirement. Systems that classify with trained parameters — statistical, neural, transformer, or LLM-based — and that therefore require training data or accumulated learner history differ from a system whose classification stage is a deterministic rule set requiring neither.
  3. Content annotation and its use. Systems that infer instructional structure by scanning content at runtime, or that require the student to self-report the locus of confusion, differ from a system in which the concept graph — topic, prerequisites, and likely misconceptions — is embedded in the instructional content at authoring time and read from scroll position at activation.
